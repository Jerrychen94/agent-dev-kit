# 07 数据与知识接入

> 适用于"agent 要用到外部数据"的项目。这是 L4 知识层里最硬的一块：知识可以模糊检索，数据不行——取不到就是取不到，取错了整篇结论都废。

## 1. 先分清三种知识

| 类型 | 例子 | 放哪 | 变了多久生效 |
|---|---|---|---|
| 稳定知识 | 领域常识、写作规范、术语表 | 系统提示、`prompts/` | 随版本发布 |
| 半稳定知识 | 文献、政策条文、内部文档 | 文件 + 检索索引 | 重建索引后 |
| 实时与权威数据 | 数据库、行情、自有问卷 | 数据源 + 连接器 | 每次取数 |

判据：**这条信息多久变一次、错了谁会发现**。写作风格写错，读者看着别扭；财务数据取错，结论直接反转。后者必须走数据源，不能塞进提示词。

## 2. 数据放哪

不要一律塞进仓库，也不要一律上云。按体量和性质选：

| 数据 | 放哪 | 入 git | 理由 |
|---|---|---|---|
| 字段字典、代码本、示例小表（<5 MB） | 项目内 `data/raw/` 或 `data/reference/` | 是 | 需要版本可追溯，且体量可控 |
| 清洗后的面板（5 MB–2 GB） | 本地 `data/derived/`，Parquet | 否 | 可再生，且读得快 |
| 授权库原始导出 | 本地 `data/raw/` | 否 | 授权禁止转发，仓库是公开面 |
| 单文件超 2 GB、需多人共享 | 对象存储（S3 / OSS / COS） | 否 | 路径写进清册，不进代码 |
| 需要反复查询的结构化数据 | 本地 DuckDB 或只读数据库 | 否 | 避免反复解析 CSV |
| 含个人信息的数据 | 本地加密盘或机构合规环境 | 否 | 只把脱敏版放进工作区 |

三条红线：

1. 原始数据不进 git；`.gitignore` 按层忽略，只保留各层的说明文件。
2. 授权数据不放公网可读的对象存储；桶默认私有，用预签名 URL 临时取。
3. 对外只给聚合结果，不贴原始记录。

**单机项目的推荐组合**：原始导出与历史快照放对象存储，本地只留 Parquet 或 DuckDB 缓存，清册里记两个地址。换机器不用搬几个 G，回查还能拿到原始文件。

## 3. 三层目录

```
data/
├─ raw/        # 原始层：只进不改，落地时记 sha256 与获取日期
├─ interim/    # 中间层：清洗与合并，可重跑
└─ derived/    # 派生层：分析就绪的面板与表格，可删可重建
```

判据：**删掉 `interim/` 与 `derived/`，不该丢任何不可再生的东西**。做不到，说明有原始数据被放到了下游。

`raw/` 下的每个数据源配一份 `MANIFEST.md`：来源与版本、获取日期、文件清单、校验和。四行就够，不要写成散文。

## 4. 多源：清册加逐源说明

多数据源项目的通病是：连接串散落在脚本里，谁也不知道现在有几个源、哪个还能用。治理办法是**一份机器读的清册加一组人读的说明**。

### 4.1 清册 `data/catalog.json`

清册是唯一事实源，只放元信息，不放数据、不放密钥：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 小写连字符，命令与代码里用它 |
| `name` | 是 | 展示名 |
| `kind` | 是 | `licensed_db` / `public_file` / `public_api` / `local_survey` / `object_storage` |
| `status` | 是 | `available` / `needs_download` / `needs_key` / `planned` |
| `granularity` | 是 | 观测单位，例如公司-年度 |
| `coverage` | 是 | 范围与时间跨度 |
| `topics` | 否 | 主题标签，给人看 |
| `keywords` | 是 | 选型匹配词，路由靠它 |
| `access` | 是 | `type`、`path` 或 `url`、`format`、`env[]` |
| `update` | 是 | 更新频率 |
| `license` | 是 | 授权与再分发限制 |
| `doc` | 是 | 逐源说明的路径 |
| `notes` | 否 | 已知坑 |

模板见 [templates/data-catalog.json](../templates/data-catalog.json)。

### 4.2 逐源说明 `data/sources/<id>.md`

每源一份，固定六节，别自由发挥——固定结构才能被快速扫读：

1. **概览表**：id、类型、状态、粒度、覆盖、更新、接入
2. **常用表与字段**：真正会被用到的那些
3. **接入步骤**：从零到能取数，编号列出
4. **已知坑**：编码、口径、缺值、版本变更
5. **合规要求**：能不能转发、能不能公开、要不要署名
6. **版本与获取记录**：指向 `MANIFEST.md`

模板见 [templates/数据源说明.md](../templates/数据源说明.md)。

### 4.3 两条纪律

- **清册是索引，说明是细节。** 清册里不复制字段清单，只给路径；否则两处会不一致。
- **声明与实测分开。** `status` 是人写的预期，`probe` 是机器测的现状。两者不一致时以 probe 为准，并回头改清册。

## 5. 连接方式

### 5.1 三种连接器

| 类型 | 适用 | 实现要点 | 典型失败 |
|---|---|---|---|
| `local_files` | 授权库导出、年鉴、自有数据 | 固定目录与文件名模式；读入时显式指定编码与列类型 | 目录为空、前导零丢失、编码错 |
| `http_api` | 公开接口、厂商 API | 超时、重试、分页、限速；响应落原始文件再解析 | 429、超时、200 带错误体 |
| `object_storage` | 大文件、快照 | 预签名 URL、分片下载、校验和 | 区域错误、过期签名、权限过大 |

需要反复查询时再加 `sql` 连接器，但只给只读账号，并把 SQL 写成常量而非模型自由生成。

### 5.2 统一接口

连接器对外只暴露三个动作，签名固定：

```
probe(source)            -> {ready: bool, checks: [{name, ok, detail}], hint}
describe(source)         -> {tables: [...], fields: [...]}
fetch(source, query)     -> {records: [...], meta: {source, fetched_at, rows}}
```

约束：

- `probe` 只查本地文件与凭据是否存在，**不发昂贵的网络请求**；要测连通性另开 `--online`。
- `fetch` 必须有超时与有限重试；失败返回结构化错误码，不抛裸异常。
- `fetch` 的结果先落 `raw/`，解析在下游做；这样接口挂了也能离线重跑。
- 返回值带 `fetched_at`，否则半年后没人说得清数据是哪天的。

### 5.3 错误约定

| 码 | 含义 | 处理 |
|---|---|---|
| `UNKNOWN_SOURCE` | id 不在清册 | 查清册可用 id |
| `CATALOG_NOT_FOUND` | 清册文件缺失 | 确认工作目录或环境变量 |
| `CATALOG_INVALID` | 清册 JSON 非法或字段缺失 | 修正清册 |
| `MISSING_CREDENTIAL` | 所需环境变量未设置 | 配置后重试 |
| `SOURCE_NOT_READY` | 文件缺失或未下载 | 按逐源说明准备 |

## 6. 按需选源

需求到数据源的映射，分三层，越往下越确定：

1. **关键词匹配**：需求文本命中 `keywords`，按命中数与就绪状态排序。优点是能解释（命中哪几个词），缺点是同义词与缩写要靠扩充词表。
2. **规则匹配**：年份覆盖、粒度、地区。例如"日频事件研究"直接排除只有年度的源。
3. **显式声明**：项目配置里锁定数据源 id，评测与产物都以它为准。

原则：**自动匹配只给候选，不给结论**。最终由人或上层编排确认，并在产物里写明用了哪个源、哪个版本。

## 7. 密钥与合规

- 清册的 `access.env` 只写变量名，不写值；值放 `.env`，`.env` 不入库。
- 权限最小化：只给目标目录或桶前缀，不给账号级密钥。
- 授权数据：不转发、不公开、不用于对外服务；论文只呈现聚合结果。
- 个人信息：先脱敏再入库；编号与身份的对应表单独存放。
- 每次取数记 `fetched_at` 与数据截止日，写进论文脚注。

## 8. 验收清单

- [ ] `data/` 按 raw / interim / derived 分层，各层有 README 说明规则
- [ ] 清册 `catalog.json` 覆盖全部数据源，`id` 唯一，字段齐全
- [ ] 每个数据源都有 `sources/<id>.md`，六节齐全
- [ ] 清册引用的说明文件真实存在
- [ ] `probe` 能区分就绪与未就绪，并给出可执行的提示
- [ ] 凭据只出现在环境变量里，仓库内无明文
- [ ] `.gitignore` 挡住了各层数据，只保留说明文件
- [ ] 选型命令能按需求给出可解释的候选顺序

## 9. 反模式

| 反模式 | 后果 | 改法 |
|---|---|---|
| 连接串与密钥写进代码 | 泄漏，且换环境就炸 | 清册记变量名，值走环境变量 |
| 原始数据提交进仓库 | 仓库膨胀、授权违约 | `.gitignore` 分层忽略 |
| 只有总体说明，没有逐源说明 | 半年后没人敢动 | 一源一文件，固定六节 |
| 用向量检索做精确字段查询 | 数值对不上，无法归因 | 该用连接器就用连接器 |
| `probe` 直接打生产接口 | 体检把额度打光 | 只查本地配置，连通性另开开关 |
| 数据源状态只在人脑里 | 重复踩同一个坑 | 清册加 `notes` 与 `status` |

参考实现：一个含八个数据源的私有 agent 项目按本节的写法落地——清册加逐源说明，`data list/show/recommend/probe` 四条命令；按次计费的接口（如万方）在对应 `sources/*.md` 里写清计费口径与欠费时的失败方式。照 [数据源说明模板](../templates/数据源说明.md) 与 [data-catalog.json](../templates/data-catalog.json) 抄一遍即可复现。
