# 02 分层模型与项目结构

## 1. 六层模型

任何 agent 都能拆成六层。分层的意义是：出问题时能定位到层，改动时知道影响哪层，评审时知道该看什么。

| 层 | 名称 | 内容 | 常见错误 |
|---|---|---|---|
| L1 | 指令层 | 系统提示、SKILL.md、角色与流程、示例 | 用长提示掩盖缺失的工具；规则写成散文而非清单 |
| L2 | 能力层 | 工具函数、MCP 工具、CLI 封装、schema | 工具返回值无结构；错误码缺失；参数靠模型猜 |
| L3 | 编排层 | 控制流、状态、重试、并行、子 agent | 用多 agent 解决上下文问题；状态藏在提示里 |
| L4 | 知识层 | 检索、记忆、数据源、新鲜度 | 把检索当万能；不区分“稳定知识”与“实时数据” |
| L5 | 评测层 | 用例集、判分、基线、回归 | 只有 happy path；无基线；手工跑 |
| L6 | 运行层 | 入口、配置、密钥、日志、成本、权限 | 配置写死；print 当日志；密钥进仓库 |

### L1 指令层

写什么：目标、边界（不做什么）、步骤顺序、输出格式、示例、失败时的话术。
判据：一个没参与开发的人读一遍，能说出“这 agent 遇到 X 会怎么做”。
反模式：靠“请务必认真地仔细分析”提升质量——这是无效指令；有效的是“如果字段缺失，输出 null 并在 warnings 里说明”。

### L2 能力层

写什么：工具签名、参数约束、返回结构、错误约定、幂等性。
判据：每个工具能在不调用模型的情况下被单元测试。
反模式：返回自然语言（模型要再解析一遍）；一个工具干五件事；工具名含糊（`process`、`handle`）。

### L3 编排层

写什么：步骤图、并行点、重试与超时、状态存放位置、人工介入点。
判据：能在纸上画出流程图；每个箭头有数据形状。
反模式：把中间状态塞进对话历史；错误直接穿透到最终输出；无限重试。

### L4 知识层

写什么：知识来源、切分策略、检索方式、更新频率、命中率。
判据：能回答“这条知识变了，多久生效”。
反模式：用检索做精确字段查询（该用工具）；不记录召回内容导致无法归因。

### L5 评测层

写什么：用例、判分、指标、基线、回归入口。
判据：改一行提示词，10 分钟内能知道变好还是变坏。
反模式：评测集与调试集同源；只数通过率不看错误类型。

### L6 运行层

写什么：入口命令、配置项、密钥管理、日志字段、成本上限、回滚步骤。
判据：换一台机器，照 README 能在 15 分钟内跑起来。
反模式：绝对路径；隐式依赖本机环境；日志无 trace_id。

## 2. 六层 × 四形态

| 层 | Skill 工作流 | MCP Server | 独立 LLM 应用 | 多 agent 编排 |
|---|---|---|---|---|
| L1 | SKILL.md 全部内容 | 工具 description | 系统提示 + 流程提示 | 各 agent 的角色提示 |
| L2 | scripts/ 下的脚本 | 工具实现（核心） | 内部函数调用 | 各 agent 的工具子集 |
| L3 | 编排放进 SKILL.md 步骤 | 单次调用，几乎无编排 | 代码里的流程 | 编排器 / 路由 |
| L4 | 读本地文件 | 资源与数据源 | RAG + 数据库 | 共享知识 + 私有知识 |
| L5 | 手工验收 + 样例 | 工具级测试 + 调用方评测 | 全链路评测（重点） | 分 agent 评测 + 端到端 |
| L6 | 依赖宿主环境 | 部署与传输（stdio/HTTP） | 服务部署、监控 | 服务编排、追踪 |

结论：Skill 的功夫在 L1，MCP 的功夫在 L2，LLM 应用的功夫在 L3+L5。不要把力气花错层。

## 3. 标准项目结构

```
<agent-name>/
├─ README.md              # 是什么、怎么跑、怎么测、依赖什么
├─ AGENTS.md              # 给编码 agent 的项目约定（可选，但有帮助）
├─ CHANGELOG.md           # 版本与变更，含 prompt 变更
├─ Makefile               # run / test / evals 三个目标
├─ .env.example           # 配置项清单（无真实密钥）
├─ docs/
│  ├─ design.md           # 设计说明
│  ├─ contract.md         # 输入输出契约、工具清单、失败模式
│  ├─ runbook.md          # 运行手册：怎么启动、怎么看日志、怎么回滚
│  └─ adr/                # 决策记录
│     └─ 0001-xxx.md
├─ src/                   # 代码（Skill 形态可为空或放 scripts/）
├─ prompts/               # 提示词单独存放，便于版本对比
├─ evals/
│  ├─ config.json         # 被测入口命令、超时、基线文件
│  ├─ cases/              # 用例，一条一个文件或 jsonl
│  └─ baseline.json       # 上次合格结果，用于回归对比
├─ scripts/               # 可复用脚本（跑评测、清洗、校验）
└─ tests/                 # 单元测试与集成测试
```

小项目可以合并 `tests/` 与 `evals/`；但 `docs/contract.md` 和 `evals/` 不要省。

## 4. 命名约定

| 对象 | 规则 | 好例子 | 差例子 |
|---|---|---|---|
| 项目目录 | kebab-case，动词或“名词+动词” | `invoice-reconciler`、`meeting-notes` | `my_agent2`、`测试1` |
| 提示词文件 | 语义化，含用途 | `system.md`、`extract-invoice.md` | `prompt_v3_final.md` |
| 工具名 | `动词_名词`，全小写 | `search_orders`、`get_invoice` | `process`、`doIt` |
| 用例 id | `类别-序号` | `extract-001`、`neg-007` | `test1` |
| 版本 | 语义化版本 | `1.2.0` | `final`、`v2新` |
| 分支 | `feat/`、`fix/`、`exp/` | `exp/rag-chunk-800` | `dev2` |

中文项目也可用中文目录名，但**代码、配置键、工具名一律英文**，避免编码与调用问题。

## 5. 版本与变更

三样东西都要版本化，且分开记录：

1. **代码**：git tag，语义化版本。
2. **提示词**：进版本库，每次变更在 CHANGELOG 写明“改了什么、为什么、指标变化”。
3. **模型与配置**：记录模型名与关键参数（温度、最大 token），模型升级视为一次变更。

规则：**提示词或模型变更 → 必须重跑评测 → 结果写进 CHANGELOG**。这是防止“悄悄变差”的唯一有效手段。

版本号约定：

- 补丁（1.0.1）：提示词微调、修 bug，接口与行为不变。
- 次版本（1.1.0）：新增工具、新增能力，向后兼容。
- 主版本（2.0.0）：输入输出契约变化，或行为语义变化。

## 6. 配置约定

- 配置从环境变量读，代码里不写死密钥与路径。
- `.env.example` 列出所有变量、用途、示例值（假值）。
- 生产与开发用不同配置，不做“改一行就切环境”。
- 所有配置项有默认值或明确报错，不要静默用 None。
