# 04 评测与质量规范

评测是这套规范的核心。没有评测，后面所有“优化”都无法判断真假。

## 1. 三层测试

| 层 | 测什么 | 数量级 | 跑多久 | 何时跑 |
|---|---|---|---|---|
| 单元测试 | 工具函数、解析、校验（不调模型） | 每个工具 ≥3 条 | 秒级 | 每次改代码 |
| 链路 smoke | 端到端一条 happy path | 3–5 条 | 分钟级 | 每次改提示或流程 |
| 质量评测 | 输出对不对、稳不稳 | ≥30 条 | 分钟到小时 | 每次要发布 |

三层缺一不可：只做单测不知道整体效果，只做评测不知道错在哪。

## 2. 评测集构造

### 来源优先级

1. 真实历史输入（最佳，带真实分布）。
2. 自己构造的边界与对抗样例。
3. 线上失败 case（脱敏后入库）。

**禁止**：用训练/调试时反复看过的样例充当评测集——分数虚高。

### 分层要求

| 类型 | 占比参考 | 说明 |
|---|---|---|
| 简单 | 20% | 典型输入，用来防退化 |
| 正常 | 40% | 真实分布主体 |
| 困难 | 25% | 长输入、歧义、多字段、格式不规范 |
| 对抗/负例 | 15% | 空输入、超长、注入文本、缺字段、不该处理的请求 |

负例与边界合计不低于 20%。负例的作用不是提高分数，而是防止系统在异常输入上胡说或崩溃。

### 数量与质量

- 起步 30 条，稳定期 50–100 条。再多要能说清每条为什么在。
- 每条必须能回答：它测的是哪一层能力？失败说明什么？
- 去重：语义重复的合并，否则分数被同一类难度主导。
- 脱敏：手机号、身份证、客户名替换为假值，但保持格式与长度。

### 用例格式

`evals/cases/*.json`，一个文件一条：

```json
{
  "id": "extract-001",
  "tags": ["normal", "invoice"],
  "input": "2026年3月发票，金额 1280.50 元，开票方：示例科技",
  "expect": {
    "contains": ["1280.50", "示例科技"],
    "not_contains": ["无法确定"],
    "json_path": {"path": "amount", "equals": 1280.5}
  },
  "notes": "金额带小数，验证不丢失精度"
}
```

`expect` 支持的断言（全部满足才算通过）：

| 断言 | 含义 |
|---|---|
| `contains` | stdout 必须包含全部字符串 |
| `not_contains` | stdout 不得包含任一字符串 |
| `regex` | 必须匹配正则 |
| `json_path` | 解析 stdout 为 JSON 后按路径取值比较（支持 `.` 路径与数组下标） |
| `exit_code` | 期望的退出码 |

`evals/config.json`：

```json
{
  "cmd": ["python3", "src/agent.py"],
  "timeout_sec": 60,
  "baseline": "baseline.json",
  "tolerance": 0.05
}
```

执行约定：**输入从 stdin 进（JSON 或纯文本），结果从 stdout 出（JSON 优先）**。这是唯一要求被测程序遵守的接口，也是 `scripts/run-evals.py` 能复用的前提。

## 3. 指标

必测：

| 指标 | 定义 | 目标 |
|---|---|---|
| 任务成功率 | 用例通过数 / 总数 | 按业务定，通常 ≥85% |
| 字段准确率 | 关键字段正确条数 / 总条数 | 关键字段 ≥95% |
| 拒答正确率 | 该拒的拒了 / 应拒总数 | ≥90% |
| 误答率 | 不该答却答了 / 总数 | 越低越好，比成功率更该盯 |
| p95 延迟 | 单次端到端耗时 | 按场景定 |
| 单次成本 | token 折算费用 | 有上限 |
| 人工介入率 | 需人工修正的比例 | 持续下降 |

只报“成功率”是不够的：成功率涨了，可能只是把该拒的都硬答了。**误答率必须单独看。**

## 4. 判分方式

优先级：确定性断言 > 规则匹配 > 人工抽检 > LLM judge。

### LLM judge 使用规范

LLM 判分可以用，但必须满足：

1. **固定 rubric**：把评分维度写成 1–5 分的明确描述，不要用“请判断好坏”。
2. **抽样对齐**：先人工标 20 条，judge 与人工一致率 ≥80% 才可用；否则调 rubric。
3. **记录版本**：judge 用的模型与提示词要记进 config，换 judge 等于换尺子，历史分数不可直接比。
4. **防位置偏差**：对比两版输出时，A/B 顺序随机，或各跑两次交换顺序。
5. **只做辅助**：judge 分数用于排序与发现退化，不作为唯一上线依据。

### 人工抽检

上线前至少抽检 20 条，覆盖四类难度。抽检记录必须留档（哪条、为什么判错、归因到哪层）。

## 5. 回归策略

- 每次全量跑完后写 `evals/baseline.json`（仅当达到阈值时更新）。
- 通过率下降超过 5 个百分点即视为回归，阻塞发布。
- 单条用例由通过变失败，必须归因到五类之一：提示 / 工具 / 检索 / 模型 / 数据。
- 归因写进 CHANGELOG：`evals: 88% → 82%，失败集中在长输入日期解析（提示类）`。

## 6. 迭代记录格式

每次调优记录一行，便于回溯：

```
## 2026-10-30 提示词加入日期格式示例
- 改动：system.md 增加 3 个日期示例；extract 提示去掉“尽量准确”类空话
- 假设：日期字段错误主要来自格式歧义
- 指标：成功率 78% → 86%；日期字段准确率 71% → 93%
- 代价：输入 token +180/次
- 结论：保留
```

## 7. 评测反模式

| 反模式 | 后果 |
|---|---|
| 只有一个大 prompt 和“感觉还行” | 无法判断退化 |
| 评测集全是 happy path | 上线即崩在边界 |
| 用调试过的样例当测试集 | 分数虚高 20–40 个点 |
| 只数通过率不看错误分布 | 修一个坏两个 |
| 同时改提示、检索、模型 | 涨跌原因不明 |
| judge 模型换了不记录 | 历史分数失去可比性 |
| 评测手工跑、不进门禁 | 一次赶时间就再也不跑 |
| 基线只记录不比较 | 回归无人发现 |
