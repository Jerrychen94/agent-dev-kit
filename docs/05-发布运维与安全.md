# 05 发布、运维与安全

前四个阶段决定“能不能做对”，这一章决定“出错时会不会很贵”。

## 1. 上线前五问

1. 它写数据吗？写错一次代价多大？
2. 它花钱吗？单次多少、一天最多多少？
3. 它出错时用户看到什么？
4. 出问题怎么关掉它、怎么回滚？
5. 日志里会留下哪些敏感信息？

五问有任何一条答不上来，不上线。

## 2. 版本与发布

- 代码打 tag（`v1.2.0`），CHANGELOG 写“改了什么 / 为什么 / 指标变化”。
- **提示词与模型参数同样算版本**，改了必须重跑评测再发。
- 配置与代码分离：同一份镜像/代码，靠环境变量区分开发与生产。
- 发布顺序：先跑通全量评测 → 小范围灰度 → 观察 → 放量。
- 灰度期重点关注：错误率、延迟、单次成本、人工修正率。

**一次只发布一个变化**。同时改提示和换模型，出问题无法定位。

## 3. 密钥与权限

| 要求 | 做法 |
|---|---|
| 不入库 | `.env` 进 `.gitignore`；仓库只留 `.env.example` |
| 最小权限 | 用只读 key 就别给写权限；按服务拆分 key |
| 可轮换 | 记录 key 归属与到期日；至少半年轮换一次 |
| 不落日志 | 日志打印前过滤 key、token、cookie |
| 传输安全 | 远程 MCP 用 HTTPS；stdio 服务不监听公网端口 |

提交前自查：`git diff` 里搜 `sk-`、`ghp_`、`AKIA`、`password`、`BEGIN PRIVATE KEY`。

## 4. 成本控制

三道闸：

1. **单次预算**：限制最大输入/输出 token；超长输入先裁剪或分段，不静默截断。
2. **日上限**：按天累计，超限拒绝并告警。
3. **熔断**：连续失败或单请求重试超限，直接终止，不无限循环。

降本手段（按性价比排序）：缓存相同请求 → 缩短提示 → 用小模型做简单步骤 → 减少检索块数 → 批量合并请求。

不要用“减少评测”来降本。

## 5. 可观测

### 日志规范（行分隔 JSON）

```json
{"ts":"2026-10-30T12:00:00+08:00","level":"info","trace_id":"a1b2","step":"extract",
 "duration_ms":1832,"model":"xxx","in_tokens":820,"out_tokens":140,
 "tool":"get_invoice","tool_args":{"id":"INV-1"},"tool_ok":true}
```

必须字段：`ts`、`level`、`trace_id`、`step`、`duration_ms`。工具调用额外记 `tool`、`tool_args`（脱敏）、`tool_ok`、`error_code`。

### 要盯的四个指标

- 错误率（按错误码分组）
- p95 延迟
- 单次 token / 成本
- 人工修正率（有交互的场景）

### 告警

只对“需要人动手”的事情告警：连续失败、成本超限、关键工具不可用。其他进日报。

## 6. 危险操作

写操作（发邮件、改状态、下单、删文件）必须满足至少一条：

- 人工确认（交互场景默认）。
- `--dry-run` 先输出“将要做什么”，确认后执行。
- 幂等键 + 可撤销（软删除、可回滚事务）。
- 沙箱/只读环境先验证。

其余要求：

- 批量操作设上限（一次最多 N 条），超出要求分批确认。
- 所有写操作留审计日志：谁、何时、对什么、改前改后。
- 不把“删除”“覆盖”做成默认行为；默认只读。

## 7. 数据与隐私

- 输入先判断是否含 PII；含则脱敏后再送模型（或明确记录已获授权）。
- 明确留存期：日志里的原始输入保留多久，到期删除。
- 对外输出的内容，不包含内部路径、密钥、其他用户数据。
- 用第三方模型时，清楚数据是否会用于训练（读服务条款），敏感场景选不训练/私有部署。

## 8. 回滚

上线前必须写好：

1. 当前可用版本号。
2. 回滚命令（一条）。
3. 回滚后如何验证（跑 3 条 smoke）。
4. 数据是否需要回补（写操作场景）。

回滚演练至少做一次。没演练过的回滚方案等于没有。

## 9. 运行手册（docs/runbook.md）

至少包含：

- 启动与停止命令、依赖服务清单。
- 常见故障与处理：模型超时、限流、工具报错、成本超限、输出格式错。
- 日志在哪、怎么查某个 trace_id。
- 回滚步骤。
- 联系人/责任人（个人项目写“我自己 + 备用方案”）。

## 10. 事故处理顺序

**止血优先于定位**。顺序：关闭/降级 → 评估影响范围 → 保留现场（日志、输入） → 修复 → 补 eval 用例 → 复盘。

不要在事故进行中重构代码。先让它不出错，再让它变好。
