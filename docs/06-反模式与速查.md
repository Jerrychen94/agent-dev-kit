# 06 反模式与速查

## 1. 十条最常见反模式

| # | 症状 | 后果 | 替代做法 |
|---|---|---|---|
| 1 | 先堆十个工具，再想流程 | 工具互相覆盖，模型选错 | 先画流程，工具只留流程需要的 |
| 2 | 用长提示词补能力缺口 | 越写越长，越改越乱 | 缺能力就加工具或加脚本 |
| 3 | 用多 agent 解决上下文太长 | 信息在传递中丢失，难调试 | 先试分块、摘要、检索 |
| 4 | 没有评测就上线 | 改一次坏一次，无人察觉 | 30 条用例 + 基线，进门禁 |
| 5 | 错误静默吞掉 | 用户看到空结果，以为没问题 | 显式报错 + 可操作提示 |
| 6 | 用模型做确定性的事 | 算错、格式漂移、成本高 | 用代码做算术、映射、校验 |
| 7 | 只测 happy path | 边界一碰就崩 | 负例 ≥20% |
| 8 | 同时改三处再测 | 不知道为什么变好 | 一次只改一类，记录指标 |
| 9 | 密钥写进代码或 `.env` 入库 | 泄漏，且难轮换 | 环境变量 + `.env.example` |
| 10 | 无成本上限 | 一次循环烧掉预算 | 单次预算 + 日上限 + 熔断 |

## 2. 提示词写法对照

| 差 | 好 | 为什么 |
|---|---|---|
| 请仔细、准确地分析 | 逐条列出字段；缺失填 null，并在 warnings 说明 | 可执行、可验证 |
| 输出格式要规范 | 输出 JSON，含 `amount`(number)、`date`(YYYY-MM-DD) | 有明确 schema |
| 如果不懂就问 | 当 `order_id` 不在输入中出现时，输出 `{"error":"missing_order_id"}` | 定义了具体分支 |
| 尽量简洁 | 只输出 JSON，不要解释文字 | 去掉了模糊判断 |
| （给 5 个示例，格式各异） | （给 2 个示例，格式完全一致） | 示例要示范同一模板 |

原则：**每句话都要能被判断真假**。不能被检验的形容词，删掉。

## 3. 工具设计对照

| 差 | 好 |
|---|---|
| `process(data)` | `extract_invoice_fields(text: string) -> {amount, date, vendor}` |
| 返回一段话 | 返回 `{"items":[...], "total":12, "has_more":true}` |
| 出错抛裸异常 | 抛 `ToolError(code="invalid_date", hint="需要 YYYY-MM-DD")` |
| 一次返回全部 | 分页 + 单页上限 |
| 参数全字符串 | 用 enum / number / boolean 收敛 |

## 4. 三个每日自查

1. 今天改的东西，**变好的证据**是什么？没有证据的改动不要合。
2. 如果它现在开始出错，我**怎么在 5 分钟内知道**？
3. 这次踩的坑，**下次怎么不会再踩**？写成用例、写进避坑清单，还是抽成脚本？

## 5. 决策速查

**要不要拆多 agent？** 三个“是”才拆：上下文真的无法共享；权限必须隔离；需要独立评审。否则不拆。

**要不要上 RAG？** 先问：知识总量是否超过上下文预算的 1/3？内容是否频繁变化？是否能接受“检索不到”这个失败模式？三个都“是”再上。

**要不要换更强的模型？** 先看错误归因：如果是提示/工具/检索类，换模型无效。模型类错误超过失败总数一半，再考虑换。

**要不要加工具？** 只有当现有工具组合无法完成、且这个动作会重复出现 3 次以上时才加。

**要不要把逻辑写进提示词？** 需要判断的写提示，需要精确的写代码。边界：判断涉及自然语言理解或模糊比较 → 提示；涉及数值、格式、顺序、状态 → 代码。

## 6. 一个“合格”的 agent 长什么样

- [ ] 一句话能说清它做什么、不做什么
- [ ] 一条命令能跑，README 写清依赖
- [ ] 输入输出有 schema，错误有 code
- [ ] 结构化日志，能按 trace_id 还原一次调用
- [ ] 评测 ≥30 条，含负例，有基线，一条命令跑完
- [ ] 失败时显式报错，有降级或提示
- [ ] 有成本上限，超限熔断
- [ ] 写操作有确认或 dry-run
- [ ] 密钥不进库，配置走环境变量
- [ ] 有 CHANGELOG，提示词变更与指标变化可追溯
- [ ] 有回滚步骤，且演练过

## 7. 术语

| 词 | 含义 |
|---|---|
| Smoke | 端到端最小验证，只证明“没坏” |
| Golden set | 固定的高质量评测集，作为回归基准 |
| Baseline | 上次合格通过的评测结果，用于对比 |
| 归因 | 把失败定位到提示/工具/检索/模型/数据五类之一 |
| 幂等 | 同一请求执行多次，结果一致 |
| trace_id | 一次请求贯穿所有步骤的标识 |
| 熔断 | 连续失败或超限后自动停止调用 |
| Dry-run | 只输出将要执行的动作，不真正执行 |
