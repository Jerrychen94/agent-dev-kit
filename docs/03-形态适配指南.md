# 03 形态适配指南

四种形态的技术栈与骨架不同，流程与质量要求相同。先判断形态，再套骨架，最后对照“必写内容”自查。

## 0. 怎么选形态

| 你的需求 | 选 | 理由 |
|---|---|---|
| 让编码 agent 按固定流程完成某类任务 | Skill 工作流 | 不需要新服务，改 SKILL.md 即可迭代 |
| 把某个系统/数据源开放给任意 LLM | MCP Server | 一次实现，多处复用，权限可集中控制 |
| 有独立产品入口、需要服务化与监控 | 独立 LLM 应用 | 完全掌控编排、UI、成本与灰度 |
| 该任务天然分角色且角色间上下文无法共享 | 多 agent | 唯一正当理由：上下文隔离或权限隔离 |

判断顺序：先问能不能用 Skill 解决（最轻），再问能不能用现成 MCP（少写代码），都不行才做应用。

## 1. Skill 工作流

**本质**：一段写给模型的作业指导书 + 可选脚本。价值在“流程约束”和“踩坑记录”，不在代码量。

### 骨架

```
<skill-name>/
├─ SKILL.md          # 必需：触发描述、流程、避坑
├─ scripts/          # 可选：确定性步骤的脚本
├─ templates/        # 可选：输出模板
└─ references/       # 可选：长文档，按需读取
```

### SKILL.md 必写内容

1. **description**：什么时候用、什么时候不用。这是唯一决定它会被调用的字段，要写触发词与边界。
2. **流程**：编号步骤，每步“做什么 + 产出什么”。步骤之间不要有隐含前提。
3. **输入约定**：需要用户提供什么；缺失时怎么办（问，还是用默认值）。
4. **输出约定**：文件放哪、什么格式、必须包含哪些章节。
5. **避坑清单**：已知会出错的地方与正确做法。
6. **自检**：交付前必须执行的检查（可执行的检查写成脚本）。

### 关键做法

- **脚本优于散文**：凡是“每次都要做同一串命令”的，抽成 `scripts/xxx.py|sh`，SKILL.md 只写怎么调用。
- **渐进披露**：SKILL.md 控制在 500 行内，长参考资料放 `references/`，让模型按需读，而不是一开始全塞进去。
- **可验证的收尾**：最后一节写“确认清单”，每条能勾。
- **写清失败模式**：依赖的外部服务不可用、文件缺失、格式不符时怎么处理。

### 常见坑

- description 写成功能概述而非触发条件 → 永远不被调用。
- 步骤写得像愿望（“仔细分析文件”）而非动作（“用 pdfplumber 提取第 1–3 页表格，输出 csv”）。
- 把 3000 行文档内联进 SKILL.md → 上下文被占满，正文反而没读进去。
- 没有自检环节 → 每次都靠人发现格式错。

## 2. MCP Server

**本质**：把能力暴露成带 schema 的工具。质量取决于工具设计，不取决于模型。

### 骨架（Python / FastMCP）

```
<server-name>/
├─ pyproject.toml
├─ README.md
├─ src/<pkg>/
│  ├─ server.py        # 注册工具
│  ├─ tools/           # 每个工具一个模块
│  └─ config.py
├─ tests/              # 工具级单测（不起模型）
└─ docs/contract.md    # 工具清单与错误约定
```

### 工具设计规范

**命名**：`动词_名词`，从调用方视角命名（`search_tickets`，不是 `db_query`）。

**description 三段式**（模型靠它决定用不用、怎么填参）：

```
做什么：按关键词与状态检索工单，返回最近 20 条。
何时用：用户问“某工单现在什么状态”或需要按条件列工单时。
限制：不支持全文检索正文，只搜标题与标签；时间范围为最近 90 天。
```

**参数**：

- 类型严格（`integer` 不要用 `string` 接数字）。
- 每个参数写描述与示例值。
- 必填项尽量少；可选参数给默认值。
- 用 `enum` 收敛自由文本；不要让模型自由发挥状态名。

**返回**：

- 结构化（JSON），字段名稳定；不要返回大段自然语言让模型再解析。
- 列表必须有 `total`、`has_more`、`next_cursor`，并限制单页条数。
- 大字段截断并标明 `truncated: true`。

**错误**：

- 分清“无结果”与“出错”：无结果返回空列表 + `total: 0`；出错抛带机器可读 code 的错误。
- 错误信息面向模型可读：说明原因与下一步（`invalid_date_format: 需要 YYYY-MM-DD`）。
- 不把堆栈直接返回给模型。

**行为**：

- 读操作幂等；写操作要求幂等键，或在 description 里明确“此操作会修改数据”。
- 设超时（默认 10–30 秒），超时返回可重试错误。
- 需要鉴权的工具，在错误里说明“权限不足”而非“失败”。

### 必写内容

工具清单表（名称/用途/输入/输出/错误码）、鉴权方式、限流与超时、部署与传输方式（stdio 或 HTTP）、版本策略。

### 常见坑

- 一个工具塞五个功能，参数互斥 → 模型填错参数。
- 返回 markdown 表格 → 模型解析不稳。
- 无分页 → 一次返回 5000 条，上下文爆掉。
- 错误用自然语言长句 → 模型无法据此重试。

## 3. 独立 LLM 应用 / 服务

**本质**：一个有状态的程序，模型只是其中一个组件。工程重心在编排、可观测、成本。

### 骨架

```
<app-name>/
├─ src/<pkg>/
│  ├─ entry.py         # CLI 或 HTTP 入口
│  ├─ flow.py          # 控制流（六层里的 L3）
│  ├─ prompts/         # 提示词
│  ├─ tools/           # 工具实现
│  ├─ retrieval/       # 检索（如有）
│  └─ observability.py # 日志、trace、成本统计
├─ evals/
├─ tests/
└─ docs/
```

### 必做设计

1. **单一入口**：CLI 与 HTTP 共用同一套 flow，不要在入口里写业务。
2. **显式状态**：中间结果用数据结构（dict/dataclass）传递，不依赖对话历史。
3. **超时与重试**：每个外部调用有超时；重试限次数并退避；重试幂等。
4. **成本核算**：每次调用记录 model、输入/输出 token、估算费用；设单次与日上限。
5. **降级**：模型不可用时返回明确错误或走规则兜底，并打标记。
6. **可观测**：一次请求一个 trace_id，串起所有步骤与工具调用。

### RAG 专项（如果用到）

- 切分：按语义边界（标题/段落），块 300–800 token，留 10–15% 重叠。
- 检索：先用元数据过滤缩小范围，再向量检索；top-k 从 5 起调。
- 必须记录“本次命中的块 id 与分数”，否则无法归因。
- 回答里引用来源编号；检索不到时明确说“资料中没有”，不要用模型记忆补。
- 建一个小型检索评测集（问题 → 应命中的块 id），单独评估召回率。

### 常见坑

- 把业务逻辑写进提示词 → 无法测试、无法复现。
- 对话历史当状态 → 长对话后行为漂移。
- 无成本上限 → 一个循环一晚烧掉预算。
- 只测最终答案，不测中间步骤 → 出错无法定位。

## 4. 多 agent 编排

**默认不做。** 只有满足以下之一才拆：

1. 子任务需要完全独立的上下文（长文档分析 + 代码修改）。
2. 子任务需要不同的工具权限（读库 / 写库）。
3. 需要独立评审（生成与校验必须由不同上下文完成，避免自我确认）。

### 拆分规范

- **每个 agent 一个 JSON 契约**：输入字段、输出字段、失败返回。编排器只认契约，不认自然语言。
- **编排器不聪明**：路由、串接、重试由代码做；不要用模型决定下一个 agent 是谁（除非路由本身是模糊判断）。
- **失败隔离**：一个子 agent 失败不应让整体崩，编排器决定跳过/重试/降级。
- **上限**：并行数、总轮次、总 token 都要有硬上限，防止互相调用死循环。
- **可追踪**：每个子 agent 的 trace_id 挂在父任务下，能还原整棵树。

### 常见坑

- 用多 agent 解决“上下文太长” → 先试检索、摘要、分块，通常够用。
- agent 间传自然语言 → 信息在传递中丢失，用结构化数据。
- 没有轮次上限 → A 让 B 做事，B 让 A 确认，无限循环。

## 5. 形态对照速查

| 检查项 | Skill | MCP | 应用 | 多 agent |
|---|---|---|---|---|
| 有明确触发条件 | 必需 | description 里 | 入口设计 | 路由规则 |
| 输入输出契约 | 步骤与格式 | schema | schema + flow | JSON 契约 |
| 结构化日志 | 轻量 | 调用日志 | 必需 | 必需（含父子） |
| 评测集 | 样例 ≥10 | 工具单测 + 调用评测 | ≥30 | 分 agent + 端到端 |
| 成本上限 | 不适用 | 限流 | 必需 | 必需（含总上限） |
| 回滚 | 改回版本 | 部署回滚 | 版本回滚 | 版本回滚 |
