# 01 Agent 开发流程规范

> 适用于本目录下所有 agent 项目：提示词工作流（Skill）、MCP Server、独立 LLM 应用、多 agent 编排。形态不同，流程不变。

## 0. 五条基本原则

1. **先跑通一条链路，再长能力。** 端到端能跑之前，不加工具、不加分支、不做 UI。
2. **评测先行。** 先定义“什么叫做对了”，再写提示词。没有判据的迭代是玄学。
3. **能单不仿多。** 一个 agent + 清晰流程能做的，不要拆成多个 agent。拆分是有成本的（上下文丢失、错误传递、调试困难）。
4. **确定性的事交给代码。** 格式转换、算术、字段映射、校验，用脚本；模型只做需要判断的部分。
5. **线上每次失败都要变成一条可复跑的用例。** 不复盘的失败会重复发生。

## 1. 六阶段总览

| 阶段 | 核心问题 | 主要产出 | 退出门禁（一句话） |
|---|---|---|---|
| 0 立项 | 解决谁的什么问题 | 需求卡 | 一句话说清输入→输出，且有可量化判据 + 5 条真实样例 |
| 1 设计 | 边界与契约 | design.md、contract.md、ADR | 工具清单定稿且每个有真实用例；写明“不做什么”；评测方案确定 |
| 2 最小链路 | 端到端能不能跑 | 一条命令 + 3 条 smoke | 一条命令复现；有结构化日志；失败显式报错 |
| 3 评测打磨 | 质量是否达标 | 评测集 ≥30 条 + 基线报告 | 达到阈值；负例不崩；连续两次结果稳定 |
| 4 上线 | 能否安全运行 | 发布说明 + 运行手册 | 上线清单全绿；可回滚；有成本上限 |
| 5 复盘 | 有没有变好 | 复盘记录 + 新用例 | 失败已入库；写出下一轮假设 |

阶段 3 应占整个周期一半以上的时间。如果阶段 3 只用了一天，大概率是评测太松。

## 2. 阶段 0：立项

产出一页《需求卡》（`templates/需求卡.md`）。必须回答五问：

1. **谁用**：自己、同事、还是对外用户。决定可靠性和权限要求。
2. **什么触发**：手动跑、定时跑、被其他系统调用、还是对话中自动触发。
3. **输入什么**：格式、大小、是否含 PII。
4. **输出什么算对**：可验证的判据。写“效果好”等于没写。
5. **错了的代价**：只是重跑一次，还是会发出错误邮件、改错数据。

**同时必须写“非目标”**（本版不做什么）。不写非目标的项目，范围一定膨胀。

**样例门槛**：收集 ≥5 条真实输入，其中至少 1 条边界或失败输入。拿不到真实样例就先别开工——说明需求还没落地。

**判据写法举例**：

- 差：识别准确率要高。
- 好：在 40 条历史工单上，金额字段完全正确率 ≥95%，日期字段 ≥90%，错误时输出“需人工确认”而不是猜。

## 3. 阶段 1：设计

产出三份文件，模板见 `templates/`：

- `docs/design.md`：思路、流程、分层选型、依赖、风险。
- `docs/contract.md`：对外契约。输入/输出 schema、工具清单、失败模式、边界、成本预算。这是后续所有测试的依据。
- `docs/adr/NNNN-*.md`：影响后续维护的关键决策（模型选型、是否上 RAG、是否拆多 agent）。

设计要求：

**能力拆解**：把任务拆成“步骤 × 确定性程度”。确定性高的步骤用代码，判断类步骤用模型，二者用结构化数据衔接。

**工具清单**：先列“要做的动作”，再判断是否需要工具。每个工具必须写清四件事：输入、输出、失败时返回什么、是否幂等。起步阶段工具数 ≤7，且每个工具至少有一个真实使用场景——没有场景的工具不要写。删工具比加工具更需要勇气。

**上下文分配**三条线：稳定规则 → 系统提示；变化的数据 → 工具实时取；海量文本 → 检索。不要把整本手册塞进提示词。

**控制流**：默认“单 agent + 顺序步骤”。只有满足以下之一才考虑拆分：需要完全独立的上下文窗口；需要不同的工具权限；需要独立评审（生成/校验分离）。拆了就要在 contract 里写清 agent 间的数据契约。

**失败设计**：为超时、空结果、工具报错、模型拒答、输入超长各写一条处理策略，并规定对外表现。默认策略是“显式失败 + 可操作提示”，不是静默返回空。

**评测方案**：此时就要定下样本从哪来、判分方式、阈值。见 `04-评测与质量规范.md`。

设计评审只问三个问题：能不能更简单？失败时用户看到什么？怎么知道它变差了？

## 4. 阶段 2：最小链路

定义：一条 happy path 从入口到输出跑通，中间至少经过一次真实模型调用和一个真实数据源/工具。

硬性要求：

- **一条命令可复现**：`make run`、`python -m xxx` 或 `./run.sh`，写进 README。不允许“要手动改三处配置才能跑”。
- **结构化日志**：trace_id、每步耗时、token 用量、工具入参与出参（脱敏）。用行分隔 JSON，不要只用 print 打散文。
- **失败显式**：错误向上冒泡并带上下文，禁止 `except: pass` 和“出错就返回空列表”。
- **3 条 smoke case** 进 `evals/cases/`，能一条命令跑完。

本阶段反模式：先做前端界面；先设计多 agent 协作；先接十个工具；先追求提示词完美。

## 5. 阶段 3：评测打磨

循环：**跑分 → 错误分类 → 只改一类 → 重跑**。

错误分类固定五类，便于归因：`提示`（指令不清、示例缺失）、`工具`（参数、返回值、错误处理）、`检索`（召回、切分、排序）、`模型`（能力不足、幻觉）、`数据`（源数据本身错）。

规则：**一次只改一类**。同时改提示和检索，分数涨了也不知道为什么涨。

评测集要求：≥30 条，分层覆盖（简单/正常/困难/对抗），负例与边界 ≥20%，每条有 id、输入、预期、标签。构造方法与判分细则见 `04-评测与质量规范.md`。

门禁：达到 design 里定的阈值；负例不崩（不崩指不报错、不胡说、按约定拒答）；连续两次运行通过率波动 ≤5 个百分点。

## 6. 阶段 4：上线

五件事：打包与环境固定、密钥与权限、成本上限、可观测、回滚。

- 依赖锁版本；配置与代码分离；`.env` 不入库。
- 写操作（发消息、改数据、下单）默认要人工确认或 dry-run 开关。
- 单次 token 预算 + 日成本上限 + 超限熔断。
- 日志可检索，保留最近 30 天的失败快照。
- 保留上一个可用版本，回滚步骤写在运行手册里。

先小范围灰度（自己或一个同事），观察 1–3 天再放量。上线检查见 `checklists/03-上线checklist.md`。

## 7. 阶段 5：复盘

每月一次，用 `checklists/04-复盘checklist.md`。三件事：

1. 线上每个 bad case 转成 eval 用例（脱敏后入库）。
2. 记录“假设 → 改动 → 指标变化”，写进 CHANGELOG 或 ADR。
3. 明确下一轮只做一件事。

## 8. 时间盒参考

| 阶段 | 个人项目 | 有外部用户 |
|---|---|---|
| 0 立项 | 0.5 天 | 0.5–1 天 |
| 1 设计 | 0.5–1 天 | 1–2 天 |
| 2 最小链路 | 1–3 天 | 2–5 天 |
| 3 评测打磨 | 2–5 天 | 5–15 天 |
| 4 上线 | 0.5 天 | 1–2 天 |
| 5 复盘 | 每月 0.5 天 | 每月 1 天 |

## 9. 可裁剪的情况

- 一次性脚本级 agent（当天用完就扔）：可合并 1–2 阶段，但失败处理不能省。
- 纯本地实验、无写操作：阶段 4 可只做密钥与成本两项，其余在 design 里注明“已知风险”。
- 借用现成 MCP/Skill 只做配置：跳过 1–2 阶段，直接进 3 阶段做评测。

裁剪必须写下来，不能默认。
